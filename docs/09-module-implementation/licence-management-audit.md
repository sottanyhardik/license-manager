## 5. Findings

### F-01 — Four balance figures for one licence (High, financial consistency) [V + A]

The same licence can show different "balance" values depending on where it is read:

1. **Canonical financial** (list, detail, balance PDF, single balance XLSX, licence export, dashboard): `opening + purchase − sale − BOE − allotment`, floored at zero — `balance_calculator.py:1664-1666` [V].
2. **Customs-style** (`calculate_balance`, `calculate_balance_for_licenses`): Credit − (BOE + allotment), no purchase or opening adjustment — used by the **bulk balance XLSX** at `license_balance_excel.py:1604` [V].
3. **Transaction running balance** (Financial Ledger PDF/XLSX): derived from transaction rows and excludes BOE and allotment consumption, per the code's own comment [A].
4. **Stored cache** `LicenseBalance.balance_cif`: written by the financial formula, read as a fallback and by non-live DB filters [A].

Impact: a licence manager comparing the list, the bulk Excel and the ledger will see disagreeing numbers. The invariant `Available = Original − Utilised − Reserved` does not hold for the financial engine, because purchase credit and the zero floor are additional terms [A, consistent with the dashboard bridge at `dashboard_summary.py:236-256`].

Status: **requires a business decision** (which figure is authoritative for each output). No code change made in this stage.

### F-02 — Expiry is checked against a stored flag, not the date (Medium–High) [V + A]

- Allocation calls `validate_license_active`, which tests `license_obj.is_expired` at `apps/license/services/validation_service.py:43` [V].
- `is_expired` resolves to the stored `LicenseFlags` row, which is refreshed on save (`signals.py:302-305`) [A].
- Consequence: a licence whose expiry date has passed but which has not been saved since may still accept allocations [A]. Not reproduced yet.
- BOE and reconciliation paths reportedly do not check expiry at all [A, grep-based; not verified].

Needed: a reproduction test with a licence past its expiry date and no subsequent save; then decide the authoritative rule (date-based at check time is the likely answer, but it is a rule change).

### F-03 — Two null-balance thresholds: ₹200 and ₹500 (Medium, business decision) [V]

- Live filter, live report flags use **200**: `views/license.py:809-814` [V, read in earlier session] and `active_dfia_report.py:119,124`, `license_report.py:124,129` [A].
- Persisted `flags.is_null` uses **500**: `services/validation_service.py:322` [V, earlier session] and `signals.py:316`, `sync_licenses.py:37,194` [A].
- Per the brief, neither is changed. Documented only. Requires an explicit business owner decision.

### F-04 — Over-utilisation guards are uneven (High for BOE path; Low for allocation path) [V + A + D]

- **Allocation UI path is locked.** `apps/allotment/views_actions.py:1098` locks the allotment and `:1192` locks the licence import item with `select_for_update` inside a transaction [V].
- **Service-layer `allocate_item` has no callers.** `apps/allotment/services/allocation_service.py:152` is decorated `@transaction.atomic` but has no call sites outside tests [V, grep]. The explorer had flagged it as an unlocked race; **downgraded to dead code**. Recommend deleting or documenting it, not relying on it.
- **BOE debit guard applies only to `INDIVIDUAL_ITEM` licences.** `apps/bill_of_entry/serializers.py:84-92` runs the balance check only when `resolve_effective_cif_mode(item.license) == INDIVIDUAL_ITEM` [V]. For other modes the serializer does not check remaining CIF. Whether a downstream service enforces it was **not verified** [A says it does not]. This is the highest-risk over-utilisation path if confirmed.
- **Zero floor hides over-utilisation.** `balance_calculator.py:1666` returns `DEC_0` for any negative result [V]. A licence utilised beyond its CIF shows 0, not a negative. The dashboard compensates with an `over_utilisation_floor` term [A].

### F-05 — Concurrency: uniqueness of allocation rows relies on application code (Medium) [A]

`InvoiceBOEAllocation` and `BOEAllotmentAllocation` have no database unique constraint. Uniqueness relies on checks under `select_for_update` in `reconciliation/services/allocation_service.py:268, 479` [A]. Not verified.

### F-06 — Stale-cache filter behaviour (Low for the list, Medium elsewhere) [A]

`filtersets.py:186` filters on `balance__balance_cif`, the stored cache. The list endpoint does not use this FilterSet (BE-04, verified earlier), so the list is unaffected. Other callers were not enumerated.

### F-07 — Two licence list implementations (Medium) [V]

`/licenses` uses the new `LicenseListPage`. `/masters/licenses` still reaches the legacy `MasterList` + `LicensesTable` path. Two code paths for the same data, with different filter behaviour, is a source of inconsistency. Options: redirect `/masters/licenses` to `/licenses`, or leave it as an explicitly labelled legacy view. Decision needed.

### F-08 — Legacy redirect still generated (Low) [A]

`/licenses/:id/balance` redirects to overview but is still linked from `MasterForm.tsx:1101` and `ReconciliationIssues.tsx:61`. Those links should point directly to the overview.

### F-09 — Unused endpoint still routed (Low) [A]

`{pk}/balance-excel-unused/` is routed although its docstring says it is no longer exposed. Confirm no frontend caller, then remove.

### F-10 — Docstring drift on list balance source (Low) [A]

`views/license.py:302` and `serializers/license.py:826-835` say the list uses `calculate_balance_for_licenses`; the code uses the financial batch. `license_balance_excel.py:1595-1598` says the bulk value equals `get_balance_cif`, which is no longer true [A]. Misleading docs contributed to F-01.

### F-11 — Schema: redundant index and missing constraints (Low) [A]

- `LicenseDetailsModel.license_number` is `unique=True` and also appears in a non-unique Meta index (`models/core.py:158-164`) [A]. Redundant; remove in a migration only after confirming no query relies on it.
- `LicenseExportItemModel` has no unique constraint and no serial number (`models/core.py:865`) [A]. Duplicate export lines are not prevented. Establish whether duplicates occur before adding a constraint.

### F-12 — Bulk XLSX has no test coverage (Medium) [A]

Nothing in the test suite references `bulk-balance-excel` or `build_bulk_balance_excel` [A, grep]. This is the path that disagrees with the canonical figure (F-01).

### F-13 — Duplicated and dead frontend code (Low) [A]

Two `licenseBalanceHelpers.ts` modules, a duplicate `OverviewTab`, and an unused `BalanceTab.tsx`.

### F-14 — Report exports compute balance per row (Medium, performance) [A]

Active and expiring report exports call `get_balance_cif` per row (`active_licenses_report.py:113,197`, `expiring_licenses_report.py:105,189`) [A]. Not measured. Needs the same batching used by the list endpoint.

### F-15 — Stale index (Low, tooling) [A]

`.claude/index/dependents.tsv` references test files that are not on disk (`test_zz_tmp_*`). The index should be rebuilt before it is trusted for blast-radius checks.

### Previously recorded, still open

- BE-05 / F-03: ₹200 vs ₹500 threshold.
