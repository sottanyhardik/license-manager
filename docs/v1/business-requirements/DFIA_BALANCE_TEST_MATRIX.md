## 1. How to read this matrix

**Columns.** ID | Area | Scenario | Input | Canonical expected | UD-002 expected (only where it differs) | Dependency | Existing coverage | Priority.

**Canonical expected.** The §4.2 reading and the Part C1 values, as the spec states them. This is not a decision on BD-01.

**UD-002 expected.** The owner's approved wording (UD-002: "Available balance = allotted entitlement − unbilled BOE utilisation − billed utilisation") applied to the same input. Shown only where it differs. "—" means the same as canonical, or no reservation term is involved. Q-022 (meaning of "allotted entitlement") is still open, so where the wording has two readings both are shown. The licence reading uses the licence entitlement. The allotment reading uses the allotment total.

**DEPENDS ON BD-xx.** The expected result turns on an open decision. Two candidate expectations are given as (A) and (B). Neither is chosen.
- For rows whose only open question is BD-01, the canonical column keeps the spec figure. The alternative appears in the UD-002 column, as the brief directs.
- For rows that depend on another BD-xx, the canonical column reads "DEPENDS ON BD-xx" with both candidates. Where the spec states a figure (Part C1), it is shown inside candidate (A).

**Candidate wording.** The decision register named in the spec (`DFIA_BUSINESS_DECISION_REGISTER.md`) is now present in this folder (it was not present when this matrix was first written). Candidate expectations for BD-02 to BD-12 are therefore derived from the spec's own wording (§3–§5) and from the code and tests cited in each row. Where a candidate is the existing behaviour, the row says so.

**Existing coverage.**
- EXISTING: a test asserts the scenario's expected value. A test with the same shape but different figures counts, and the difference is named.
- PARTIAL: some assertion exists. The missing piece is named.
- MISSING: no assertion found. "Closest" names the nearest test.
- A test whose body is only `pass` is reported as MISSING, not as coverage.

**Paths.** Relative to `backend/apps/` unless shown otherwise. Example: `license/tests/test_balance_calculator.py::test_unlinked_allotment_quantity_still_counted`.

**Priority.** P0 = financial or security. P1 = core. P2 = other.

**Expected-failure notes.** Where existing code is known to differ from the canonical expectation, the difference is recorded in section 9 and referenced from the row. Nothing is changed.

## 9. Expected-failure notes (existing code differs from the canonical expectation)

These are recorded, not changed. Each one is a candidate for the owner to rule on through BD-01 to BD-12. A test that pins existing behaviour will fail if the canonical reading is adopted.

- **EF-1. Three balance figures for one dataset (TM-043, TM-088).** On the D2 fixture the code gives 93,000 (`calculate_balance`, hidden excluded), 63,000 (`calculate_customs_balance`, hidden included) and 48,000 (`calculate_financial_balance`). The snapshot's `customs_balance` reads the 93,000 figure, while the customs ledger reads 63,000. Spec A1 requires one definition per figure. The D2 characterisation tests pin all three values and endorse none.
- **EF-2. Whole-BOE exclusion once any row is invoice-matched (TM-048, TM-102).** `calculate_debit` excludes every debit row of a BOE when one row is matched to an invoice (`test_debit_excluded_for_whole_boe_once_any_item_is_invoice_matched`, and `test_boe_spanning_two_items_only_one_invoice_matched_excludes_both`). Spec §3.4 says uninvoiced portions continue at BOE value. The system audit (`docs/v1/system-audit/08-financial-business-logic-audit.md`, ISS-020) reports the same pattern for a legacy-tagged partial bill, where the unbilled amount drops out.
- **EF-3. Non-netting balance path (TM-047).** The docstring of `calculate_balance` in `apps/license/services/balance_calculator.py` says the BOE debit is the full raw CIF of every non-hidden debit row, with no invoice netting. On Ex5 that path gives 50, where the canonical figure is 55.
- **EF-4. Clamp at zero (TM-064, TM-100, TM-008).** `calculate_balance` and `calculate_all_components` floor the balance at zero, and `test_calculate_all_components_negative_balance` pins that. This hides over-utilisation and matches neither BD-08 option.
- **EF-5. Zero-CIF fallback to licence-level CIF (TM-009, TM-102).** Two `bl_ledger_03` tests pin the fallback. They fail if BD-06 option (A) is adopted.
- **EF-6. Unlinked BOE and sale both deducted (TM-062).** `test_debit_double_counts_when_boe_not_linked_to_matching_trade` pins the double deduction. The consolidated decision register records R2-04 as confirmed (UD-002 amended for this case), while `docs/v1/system-audit/execution/user-questions-register.md` shows Q-016 as PENDING_USER. This is flagged, not resolved.
- **EF-7. Overview-items view echoes stored fields (TM-059, TM-086, TM-093).** `test_balance_formula_total_minus_debited_minus_allotted` checks that the response equals stored values (`debited_quantity`, `allotted_value`). It does not show that those stored values are derived from the engine.
- **EF-8. Parity stubs (TM-081, TM-092).** `license/tests/test_cross_output_parity_option_c.py` contains 14 test bodies that consist only of `pass` with TODO comments. They report as passing with no assertions. They are not counted as coverage anywhere in this matrix.
- **EF-9. Null DFIA list boundaries (TM-089).** The list test uses 199.00, 200.00 and 201.00. The consolidated register asks for 199.99, 200 and 200.01.
- **EF-10. Q-017 register conflict (TM-090).** `consolidated-decision-register.md` records option A for Q-017 as confirmed. `user-questions-register.md` records it as PENDING_USER. This matrix treats Q-017 as open, as the brief directs.
