# API action and workflow traceability map

This register adds action-level evidence to the generated [API operation register](api-operation-register.tsv). It deliberately does **not** overwrite its `To reconcile` fields: an imported service is not proof that every action invokes it, and a test filename is not proof of complete contract coverage.

## Scope and method

**Verified by runtime/OpenAPI register.** The current schema has 354 operations. The first two sections below cover 294 operations: the initial 155-operation business-workflow set plus 17 auth/user, 105 master-data, 6 peer-sync, 4 dashboard/suggestion/ledger-upload/status, and 7 root-report operations. The final section closes the remaining 60-operation family denominator. The exact operation IDs and method/path pairs remain authoritative in `api-operation-register.tsv`.

**Verified by code.** View/action ownership, declared permission classes, direct imports, transaction blocks, and selected input/error paths were inspected at the cited symbols. **Verified by test** means a currently existing named test module exercising the capability was discovered; it does not mean every listed operation is covered. “Partial” is the required status unless the individual operation has an action-level request/response, authorization, mutation and negative-test contract.

| Status | Meaning |
| --- | --- |
| Verified registration | Resolver/OpenAPI proves a method/path and callback view. |
| Partial action map | The action family is source-inspected, but individual operations or consumers/tests still require reconciliation. |
| Contract required | V1 must add or characterize a request/response, failure, permission and recovery contract before changing the behavior. |

### Protected media is a directly registered operational entry point

`GET /api/media/<path>` is API-269, registered directly in `lmanagement/urls.py` and represented in the current OpenAPI register. `ProtectedMediaView` (`apps/core/views/media.py:102`) confines the real path under `MEDIA_ROOT`, returns 404 for traversal/missing/disallowed protected business files, and applies the owning licence/BOE/trade/company read role for recognized prefixes. Production can return `X-Accel-Redirect`; development streams the file. `test_protected_media_view.py` explicitly covers role denial, permitted roles, orphan ownership and traversal-related behavior. This hardens role-based document access; it still does not prove a tenant/company isolation policy.

## Authorization and isolation evidence

The base role class makes safe requests role-gated and write requests manager-gated; superusers bypass the role check. That is **role authorization**, not a blanket object/company predicate. Two action-level facts change the risk profile:

1. BOE transfer-letter and invoice-number actions override the normal view permission.
2. Ledger package jobs apply requester ownership, while `LicenseLedgerViewPermission` expressly has no company-assignment prerequisite.

Accordingly, every family remains **Partial** for company/object isolation until decision D1 and direct negative API tests define the policy. Existing multi-company read behavior must not be silently converted to tenancy by documentation or refactoring.

## Closure accounting

This map advances source-family evidence for **354/354 operations**. It does not claim individual contract completion for those operations: registration/callback ownership is complete for all 354, but complete individual action authorization, service effects, consumers and test mapping remains **0/354**. The family map is a bounded starting point for M1, not a substitute for individual DTO, policy, negative-path and acceptance evidence.

For each individual operation, M1 closure requires: request/response DTO, permission/action override, queryset/object scope, service/model effects, transaction/task boundary, error/edge matrix, known frontend/external consumer, test IDs and acceptance criterion. A row may only become `Verified` after each field has direct code/test/runtime evidence.
