# P0/P1 frontend action contracts

This bounded register follows selected high-risk P0/P1 pages from registered
route through the actual frontend request code, local state branches, and
named test evidence. It supplements—not replaces—the complete 57-route
static map and 49-route P0/P1 register. No row records browser observation:
the only observed routes remain `/login` and `/bill-of-entries` in the
route-workflow map.

Evidence labels: **C** = inspected source; **T** = named existing test;
**R** = registered-route/OpenAPI evidence from the existing registers;
**P** = V1 acceptance proposal; **D** = owner decision. `Partial` means that
at least one of server-side authorization/object scope, live interaction,
negative/recovery test, or business-effect proof is still missing.

## Traceability and implementation consequences

1. The shared generic `MasterList`/`MasterForm` implementations concentrate
   separate business policies. A visual refactor must first split their
   action capability matrix and preserve each entity’s request/payload/error
   behavior.
2. Allocation, trade correction, reconciliation recalculation and licence
   overview actions are consequential; their client success state is not proof
   that a database transaction or background task reached its intended final
   state. Their backend contract rows and critical-workflow tests remain
   required.
3. Server denial must be tested directly for every write/export/download.
   Client role gates and hidden buttons are defense-in-depth only, especially
   while D1 remains unresolved.
4. The document is deliberately a source-level trace. The next closure slice
   should attach exact component-test IDs and repaired browser tests to the
   P0 mutations, then record real browser observations without exposing
   business data.
