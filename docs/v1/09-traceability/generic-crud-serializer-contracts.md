# Generic CRUD, serializer, filter and pagination contracts

This bounded direct-source review covers **15 shared contracts** that shape
generated or inherited CRUD behavior across licence, allotment, BOE, trade and
master-data routes. It does not establish that every generated viewset uses
the same configuration, serializer, query path or permission override.
`C` is current-code evidence, `T` is a named current test, `S` is static
dependency evidence, and `P` is a V1 proposal. Every row remains **Partial**.

## Boundary warning

`MasterViewSet.create_viewset` dynamically creates subclasses. Static endpoint
inventory can resolve callbacks, but it cannot prove inherited behavior,
per-subclass `filter_config`, serializer fields, MDS activation, queryset or
permission overrides without an action-level inspection. Client route gates
are likewise not DRF authorization. D1 is required before treating a role-wide
query result as an object/company policy defect or guarantee.

## V1 guardrails

1. Treat generated CRUD configuration as an API contract. A viewset factory
   does not make different entities interchangeable.
2. Retain role authorization, object/company query scope, serializer field
   exposure and export access as separate checks. A UI gate or generic
   permission class cannot close all four.
3. Before any shared filter/pagination refactor, characterize malformed input,
   filter/default ordering, list metadata, empty data and large export behavior
   for every affected operation.
4. Keep MDS delegation, nested serializer writes and document/export behavior
   behind action-level transaction/recovery tests; do not rely on generic DRF
   defaults for atomicity.

This register adds 15 bounded contracts only. It does not change the complete
API, route, backend-symbol or policy-approval denominators.
