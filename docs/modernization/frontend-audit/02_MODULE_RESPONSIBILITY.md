## 3. Navigation fragmentation analysis per module

The candidates below regroup surfaces that already exist as routes/components; no new capability is implied. "Today" cites the files that already render the content. Role sets must be kept identical to today's guards (section 1) when tabs are gated.

### 3.1 Licenses
Today the licence is split across: list with inline expand panels (`LicensesTable.tsx` with `LedgerTab`, `BalanceTab`), an edit form (`MasterForm`), an Overview page with 6 tabs (`LicenseOverviewPage.tsx:33-40`: Overview, BOEs, Allotments, Planning, Items, Invoice Ledger), a "balance" route that is only a redirect, and a ledger detail page (`/license-ledger/:licenseId`, `LicenseLedgerDetail`). Overlap: `LedgerTab` and `BoesTab` duplicate BOE rendering (`BoesTab.tsx:46` states it was copied from `LedgerTab`); `LicenseBalanceModal` (1059 lines) re-presents balance a third way.
Candidate workspace `/licenses/:id` tabs: Overview, Edit details (current `MasterForm` licence form), BOEs, Allotments, Planning (existing `PlanningEditor`), Items, Invoice Ledger (existing six), plus Ledger (`LicenseLedgerDetail` content) and Documents (already fetched by `licenses/:x/documents|merged-documents`). Gates: edit and planning edit remain `LICENSE_MANAGER`; viewers keep read tabs.

### 3.2 BOE
Today: list (`MasterList`) with inline invoice/product-name edits and dispute resolve, separate edit form with parse-PDF panel and merge modal, separate transfer-letter page and also a modal (`TransferLetterModal`).
Candidate: BOE detail tabs Details (form), Items/Invoice (the inline invoice edit already in the list), Transfer letter (existing `TransferLetterForm`), Merge (existing `BoeMergeModal`). Guard note: ACCOUNT_ACCESS currently edits only invoice number; TL_GENERATE only the letter (`BOE_TRANSFER_LETTER_ROLES`).

### 3.3 Allotments
Today: list, edit form, and a separate 1833-line allocate page, with cross-links between edit and allocate (`AllotmentAction.tsx:876`). The same edit/allocate pair is reached from list buttons (`MasterList.tsx:1445,1482`).
Candidate: Allotment workspace tabs Details (form), Allocate (existing `AllotmentAction` with its available-licenses table), Documents/Export (existing PDF/Excel exports `allotment-actions/:x/export-*`, `generate-pdf`). Allocate and delete-item stay `ALLOTMENT_MANAGER`.

### 3.4 Allocations / reconciliation
Today: `/reconciliation` already is a tabbed workspace (7 tabs plus audit log, `ReconciliationPanel.tsx:154-163`) with a separate read-only `/reconciliation-issues`, and its rows hand off to trade/BOE edit pages and back. Allocation itself lives on the allotment page (3.3).
Candidate: fold Issues into the existing panel as a read-only view of the same summary (both call `reconciliation/summary/`); keep row actions opening trade/BOE in place (those editors exist as components/pages) so the flow does not leave the tab. Prerequisite already in the code: tabs are lazily fetched on activation (`useReconTabQuery.ts` comment) but only page 1 (50 rows) of each is displayed (00, 7.2 #6).

### 3.5 Trades / invoices
Today: list with grouped linked trades and modals (link, unpair, transfer letter), a 1644-line form per trade, counterpart on a second URL, and a purchase-trade upload/recover flow in ledger services.
Candidate: Trade workspace tabs Details (`TradeForm`), Counterpart (the linked trade already loaded via `counterpart_info`), Documents (bill of supply, purchase invoice, transfer letter generation endpoints already on the form). Gates stay `TRADE_MANAGER` for write, `TRADE_VIEWER` list-only.

### 3.6 Incentive licences
Today: list table and the shared `MasterForm`. Small, self-contained; no fragmentation beyond list/edit. Candidate: none beyond the list/detail pair; keep as is.

### 3.7 Ledger
Today: five pages for one subject: upload, ledger list (license-wise cards), ledger detail, download-requests list, request detail, package readiness (6 routes). Requests list and detail pages are minified single-line components. Entry to requests is a link in `LicenseLedger.tsx:580` and `reportEntities`, not the primary nav.
Candidate: Ledger workspace tabs Browse (`LicenseLedger`), Upload (`LedgerUpload`, `LEDGER_UPLOAD_ROLES`), Package requests (`LicenseDownloadRequests` + detail + readiness as in-tab drill-down, readiness keeps `LEDGER_PACKAGE_READINESS_ROLES`, i.e. no viewer). Per-licence ledger detail could be shown from the licence workspace Ledger tab (3.1) since both use `license-ledger/:x`.

### 3.8 Planning / SION
Today: `/planning` workspace (per-SION rules, strategy editors) and the same `PlanningEditor` embedded in the licence Overview "Planning" tab; SION norm card in Overview; PlannedReport and SION norm reports elsewhere.
Candidate: two tabs in one Planning workspace: Rules (per-SION `LicensePlanningWorkspace`) and Licence plan (`PlanningEditor`, today reached via a licence). Reports remain under Reports.

### 3.9 Reports
Today: 11 routes under the Reports menu, each a full page; four SionE pages are 10-line wrappers of `SionNormReport` with a different `sionNorm` prop; `ExpiringLicenses`/`ActiveLicenses` are 24-25 line wrappers; `DownloadLicense` also calls the same expiring/active endpoints (`DownloadLicense.tsx:86-87`).
Candidate: a Reports workspace with a report selector (existing `REPORT_ROUTES` table) and tab groups: Stock/Balance (Item pivot, Item report, Planned report), SION norms (E1, E5, E126, E132 via the one component), Licence status (Expiring, Active, Download), Profit (Purchase profit). Guard is uniform `REPORT_ROLES`, so a single gate suffices.

### 3.10 Masters
Today: one route family with generic cards, list/create/edit as separate pages, admin-only writes. Candidate: none required; a master-entity selector tab strip is already implied by `masterEntities` (9 entries, `routes/config.ts`). Edit may open in the same page as a panel; guard `USER_ADMIN_ROLES` unchanged.

### 3.11 Dashboard
Today: one page of role-conditional tiles that navigate away. Candidate: none; it is an entry surface, not a workspace.

### 3.12 Settings / Users / Tasks
Today: `/settings` (superuser user CRUD in a modal, `Settings.tsx`), `/admin/users` (+ create + edit pages), `/admin/activity-log`, `/profile`, and a global task drawer. Two overlapping user CRUD UIs with different guards.
Candidate: Admin workspace tabs Users (one implementation, presently duplicated in `Settings.tsx` and `UserList/UserForm`; business decision needed on which guard prevails, so this is flagged rather than assumed), Activity log (`ActivityLog`), MDS status (`MdsStatusCard`), and Profile separate (all-user). Tasks stay a global drawer.
