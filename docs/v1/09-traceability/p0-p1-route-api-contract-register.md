# P0/P1 route-to-API contract register

This implementation register covers every route marked P0, P1, or P0/P1 in [frontend-route-workflow-map.md](frontend-route-workflow-map.md): **49 route IDs represented by 45 contract rows** (the four SION report aliases and two ledger-detail aliases share page implementations). The `API-*` references are exact current OpenAPI register IDs where available. A request path visible only in frontend source but absent from the generated schema is deliberately marked **schema gap**, not invented as a contract.

## Required test form

Each row requires an authenticated browser/component test plus an API-level test. `L/E/S/D` means loading, empty, success, and denied states. For mutations, add an idempotency/concurrency or stale-data case where the row identifies a consequential effect. “Wrong role” means an authenticated role outside the backend operation's approved policy; it must not be substituted by a frontend `ProtectedRoute` assertion. Company/object tests must implement the owner-approved D1 policy; current code is role-oriented and no tenant conclusion is implied here.

An individual row exits **Partial** only when: (1) named operation IDs have a request/response/error fixture; (2) an anonymous and wrong-role direct API test has the approved outcome; (3) every listed UI state is run against a browser route; (4) mutation data effects are asserted and cleaned up; and (5) the route/API operation records link to the new tests. Until then these are implementation-ready acceptance gates, not verification claims.

## Register completeness

The register contains all 49 P0/P1 UI IDs from the route map, including the four routes explicitly labelled P0/P1 (UI-021, UI-025, UI-032, UI-045). It does not relabel a schema gap as an API contract. The implementation task must either reconcile those gaps to an existing `API-*` row or add a controlled OpenAPI/route disposition with compatibility tests.
