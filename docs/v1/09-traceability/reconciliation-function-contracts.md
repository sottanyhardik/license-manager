# Reconciliation function contracts

This is a bounded direct-source review of **16 reconciliation, allocation and
BOE-correction contracts**. It complements the 8,046-symbol denominator; it
does not provide a complete caller graph or promote any endpoint, model or
function to `Verified`. `C` means current-code evidence, `T` means the named
current test establishes a narrow scenario, `S` means static dependency
evidence only, and `P` is a V1 proposal. Every row remains **Partial**.

## Invariants established by the selected sources

**C:** invoice-to-BOE and allotment-to-BOE consumption are separate tracks.
The former reduces invoice-side capacity; the latter reduces allotment-side
capacity. A physical BOE debit is not a shared allocation pool. The
allocation service explicitly requires an atomic write and creates a
`ReconciliationLog` record in that same transaction.

**C:** reconciliation write endpoints use `ReconciliationPermission`. Its
role gate is evidence of API authorization, not company/object authorization;
the view performs raw PK lookup. D1 remains required before either permitting
or forbidding cross-company access is called correct. D2 and D5 likewise
remain unresolved for balance and accounting interpretations.

## V1 guardrails and closure order

1. Preserve the dual independent consumption tracks and immutable
   supersede/reverse history until D2-approved golden data proves a proposed
   change safe.
2. Add direct API tests for anonymous, wrong-role, partial dual-role, valid
   role and the D1-approved same/cross-company object cases for every write.
3. Race public allocation and merge requests; assert no over-allocation,
   orphaned history or partial log survives a failed transaction.
4. Specify the API-290 scope contract: reject `license_ids`, implement
   scoped semantics with audit, or document the all-licence behavior in UI;
   do not silently retain a misleading field.
5. Treat `ReconciliationLog` as evidence of current application behavior,
   not compliance-grade audit proof, until D6 defines retention and delivery
   requirements.

This register adds 16 bounded contracts only. It does not change the static
backend denominator, complete API/route contract count, or unapproved policy
status.
